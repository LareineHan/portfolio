# False Positive Validation & Detection Tuning

_Sanitized portfolio case study collection (ISS/ITS) — Spring 2026_

## Context

Many phishing detections generated by automated security tooling were legitimate emails incorrectly classified as malicious.

While malicious detection is critical, excessive false positives can:
- disrupt normal operations
- reduce trust in security tooling
- increase analyst fatigue
- create unnecessary remediation work

This investigation series focused on validating suspicious detections using:
- authentication review
- infrastructure verification
- sandbox behavior
- telemetry correlation
- platform legitimacy analysis

---

## Problem

Determine:
- Was the detection truly malicious?
- Was the infrastructure compromised or behaving normally?
- Did the alert originate from fingerprints/reputation rather than malicious behavior?
- Could the emails safely be released and submitted as clean?

---

## Constraints

- Automated detection systems can heavily rely on:
  - fingerprint similarity
  - reputation feeds
  - behavioral heuristics
- Shared infrastructure can trigger detection overlap
- Legitimate SaaS/education/political platforms often resemble phishing workflows
- Incorrect release decisions carry operational risk

---

## Investigations

---

## 1) Microsoft Store Campaign False Positive

### Initial Detection
A Microsoft-related campaign was quarantined as phishing.

### Initial Concerns
- URLQuery flagged suspicious indicators
- Detection engines classified the message as malicious

### Validation Findings
- Authentication aligned normally
- Infrastructure routed through legitimate Microsoft services
- Flagged indicators traced back to legitimate Microsoft CDN/JavaScript resources
- No malicious behavior observed in sandbox testing

### Outcome
- Released from quarantine
- Submitted to Microsoft as clean

### Lesson
Reputation-engine detections alone are insufficient for escalation.

---

## 2) Canvas / Instructure Notification False Positive

### Initial Detection
Canvas notification emails from:
```text
notifications@instructure.com
```

were quarantined as phishing.

### Validation Findings
- SPF/DKIM passed
- URLs and IP ranges matched legitimate Canvas infrastructure
- Content aligned with real academic workflows
- Professor/student context validated legitimacy

### Outcome
- False positive confirmed
- Released and submitted to Microsoft as clean

### Lesson
Fingerprint similarity can misclassify legitimate educational notifications.

---

## 3) Political Fundraising Campaign False Positive

### Initial Detection
Political fundraising emails were quarantined as phishing.

### Validation Findings
- Domain registration appeared legitimate
- Linked infrastructure tied to ActionNetwork
- Authentication aligned normally
- Content consistent with real political fundraising workflows

### Outcome
- Released from quarantine
- Submitted as clean

### Lesson
High-volume emotionally persuasive messaging is not automatically malicious.

---

## 4) Educational Digest / AOTA Validation

### Initial Detection
Educational digest-style emails triggered malicious verdicts due to:
- embedded media
- external URLs
- reputation-engine detections

### Validation Findings
- URLs resolved to legitimate media resources
- Infrastructure behavior matched expected educational/newsletter workflows
- No malicious behavior observed in sandbox testing

### Outcome
- Released as false positive
- Detection submitted back to Microsoft as clean

### Lesson
Legitimate content aggregation can resemble phishing telemetry patterns.

---

## Operational Workflow

Across cases, validation involved combinations of:

- SPF/DKIM/DMARC verification
- sender infrastructure review
- URL behavior validation
- sandbox investigation
- telemetry correlation
- identity context review
- delivery behavior analysis
- platform legitimacy assessment

---

## Evidence (Sanitized)

- Legitimate Microsoft infrastructure flagged as suspicious
- Canvas educational notifications misclassified
- Political fundraising campaigns quarantined incorrectly
- Educational digest traffic falsely matched malicious fingerprints

---

## Outcome

- Multiple legitimate campaigns safely released
- Detection feedback submitted to Microsoft
- Reduced unnecessary quarantine/remediation actions
- Improved operational trust in security workflows

---

## Impact

- Expanded analyst workflow from “detect malicious” → “validate legitimacy”
- Reinforced evidence-based release decisions
- Reduced operational disruption caused by over-aggressive detections
- Improved understanding of detection-engine limitations

---

## Lessons Learned

- False positive validation is as operationally important as malicious detection
- Authentication pass/fail alone is insufficient
- Sandbox behavior provides stronger evidence than reputation feeds
- Shared infrastructure requires context-aware analysis

---

## Next Steps

- Improve repeatable false positive validation workflows
- Expand sandbox-assisted verification procedures
- Continue building detection-tuning methodologies
- Improve balance between security enforcement and operational continuity

## KQL Used (Sanitized)

### Query A — Authentication review

```kql
EmailEvents
| where SenderFromAddress contains "instructure"
| project Timestamp, SenderFromAddress, AuthenticationDetails, LatestDeliveryLocation
| order by Timestamp desc
```

### Query B — Infrastructure validation

```kql
EmailEvents
| where SenderIPv4 != ""
| summarize Count=count() by SenderIPv4, SenderFromAddress
| order by Count desc
```

### Query C — Delivery outcome review

```kql
EmailEvents
| summarize
    Inbox=countif(LatestDeliveryLocation contains "Inbox"),
    Quarantine=countif(LatestDeliveryLocation contains "Quarantine")
    by SenderFromAddress
```
